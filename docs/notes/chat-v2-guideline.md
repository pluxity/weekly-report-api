# chat-v2 LLM Tool Calling 개발 가이드라인

> 로컬 작업 문서. **커밋 제외.** (작성: 2026-07-28)
>
> 이 문서는 `/chat/v2`(tool calling 조회 루프 + structured output 생성)를 **어떻게 만들고 어떻게 고칠지**를 정한 규약이다.
> 지금까지의 코드를 버리지 않고, 이 규약을 기준선으로 놓고 위반 항목만 하나씩 수렴시킨다.

---

## 0. 이 문서의 사용법

- **7개 축**이 상위 가이드라인이다. 모든 설계·수정 판단은 이 7개 중 하나에 귀속되어야 한다.
- 각 축은 네 부분으로 되어 있다:
  - **원칙** — 지켜야 할 것
  - **판정 기준** — 예/아니오로 답할 수 있는 질문. 이게 없는 조항은 조항이 아니다
  - **현 코드 상태** — 지킴 / 위반 / 미확인
  - **조치** — `A-n` 형태의 백로그 항목. §8에 우선순위로 모아둔다
- **판정 기준이 애매하면 그 조항은 지켜지지 않는다.** "잘 설계한다", "명확하게 쓴다" 같은 문장은 이 문서에 넣지 않는다.
- 코드를 고칠 때마다 해당 축의 "현 코드 상태"와 §8 백로그를 갱신한다. 살아있는 문서다.

### 왜 이 문서가 필요했나

`chat-v2-prompt.txt` 37줄 중 **9줄이 금지문**(`~하지 말 것` / `반드시` / `절대`)이다. 그 9줄은 과거 실패 9건의 화석이고,
각각은 "이 실패를 프롬프트 말고 다른 데서 막을 수 있나?"를 묻지 않은 채 추가됐다.
이 문서의 목적은 **실패가 프롬프트로 흘러가기 전에 아래층에서 걸러내는 절차를 고정하는 것**이다.

## 1. 아키텍처 — 모델과 실행을 분리하라

### 원칙

모델은 **제안만** 한다. 애플리케이션이 통제권을 놓지 않는다.

```
모델: "search_items를 이 인자로 부르고 싶다"   ← 제안 (신뢰하지 않음)
  ↓
앱:  인자 파싱 → 검증 → 허용 판정 → 실행 → 결과 반환   ← 통제 (100% 결정적)
  ↓
모델: 결과를 읽고 다음 제안 또는 최종 답변
```

파생 규칙 세 개:

1. **루프의 소유자는 앱이다.** 종료·반복·상한 판정은 모델이 아니라 서버가 한다.
   모델이 협조하지 않아도 루프는 유한 시간에 끝나야 한다.
2. **실행층에 LLM 금지.** 핸들러(조회·집계·이름 해소) 안에서 LLM을 부르지 않는다.
   실행층이 결정적이어야 단위테스트로 덮을 수 있다.
3. **3층 분리를 유지한다.**
   ```
   [라우팅]  LLM   어떤 도구를 어떤 인자로   ← 확률적. eval로 통계 측정
   [실행]    코드  조회·권한·집계·해소       ← 결정적. 단위테스트로 못 박음
   [서술]    LLM   결과 → 자연어             ← 확률적. eval + grounding 체크
   ```
   **개선이란 확률적 구간의 일을 결정적 구간으로 옮기는 것이다.** 옮길 때마다 테스트로 덮을 면적이 늘어난다.

### 판정 기준

- [ ] 모델이 협조를 거부하면(같은 걸 계속 부르거나, 끝내지 않거나) 이 루프는 **언제 끝나는가?** 답이 없으면 미완성.
- [ ] 핸들러 안에 LLM 호출이 있는가? 있으면 위반.
- [ ] 이 동작을 **LLM 없이** 테스트할 수 있는가? 없으면 실행층 설계가 잘못됐다.

### 현 코드 상태

| 항목 | 상태 | 근거 |
|---|---|---|
| 통제권 분리 | **지킴** | `ChatV2Controller` → `ChatV2Service`(루프 소유) → `ChatV2ToolExecutor`(dispatch) → 핸들러 7종. 모델은 `tool_calls`만 반환 |
| 실행층 무-LLM | **지킴** | 핸들러 7종 전부 기존 서비스 호출만. LLM 의존 없음 |
| 알 수 없는 도구 이름 | **지킴** | `ChatV2ToolExecutor.execute`의 `else -> errorResult("알 수 없는 도구")` |
| 스텝 상한 | **지킴** | `MAX_STEPS = 8`, 초과 시 예외가 아니라 안내 reply |
| **동일 호출 반복 차단** | **위반** | `toolCalls.forEach`가 무조건 실행. 같은 `(name, arguments)`를 8번 불러도 8번 실행하고 8번 과금 |
| 사용자 동시 요청 | **지킴** | `ChatV2UserLock`(`chat:lock:{userId}`, 30s) — v1과 같은 키라 v1/v2가 유저 안에서 직렬화 |

### 조치

- **A-1** 동일 `(tool, arguments)` 재호출 감지 → 실행하지 않고 다른 문구의 error로 되돌린다.
  ```kotlin
  // ChatV2Service.runLoop — 턴 단위 seen 집합
  val seen = mutableSetOf<Pair<String, String>>()
  ...
  val toolResult =
      if (!seen.add(call.function.name to call.function.arguments)) {
          support.errorResult(
              "같은 인자로 이미 호출했습니다. 결과는 위에 있습니다. " +
                  "인자를 바꾸거나, 지금까지의 결과로 답하세요.",
          )
      } else {
          toolExecutor.execute(...)
      }
  ```
  진행이 없음을 **서버가 판정한다**는 원칙의 최소 구현이다.

## 2. 도구 설계 — 스키마와 설명이 곧 프롬프트다

### 원칙

1. **도구는 배타적으로.** 두 도구의 용도가 겹치면 모델은 반드시 틀린다.
   겹침을 프롬프트로 설명하는 순간 그건 도구 경계가 잘못됐다는 신호다.
   > 선례: `get_item_details`를 `search_items`의 `detail` enum으로 흡수(6-tool 확정, d3a2738).
   > 도구를 하나 없애고 enum 한 칸으로 접은 것 — 이 방향이 맞다.
2. **인자는 타이트하게.** 자유 텍스트 < 이름(서버가 해소 가능) < enum/bool. 오른쪽으로 갈수록 hallucination 여지가 줄어든다.
3. **도구 개수 예산 = 7개.** (업계 경험칙상 20~30개를 넘기면 무관한 도구가 후보에 올라 정확도가 떨어진다.
   지금은 여유가 크지만, 예산을 미리 박아둬야 "일단 하나 더 추가"가 막힌다.)
   늘리려면 기존 도구를 흡수하거나 삭제한다. 그래도 넘치면 **카테고리별 단계적 노출 / 상황별 동적 주입**을 검토한다.
4. **description은 최소로.** 스키마는 스텝 수만큼 곱해지는 입력 비용이다. 행동 규칙은 프롬프트에 한 번만, description은 "무엇을 하는 도구인지"만.

### 인자 설계 3분류 (핵심)

모델이 만들어도 되는 값은 셋뿐이다.

| 종류 | 예 | 안전한 이유 |
|---|---|---|
| ① 닫힌 집합에서의 선택 | `type: [task,epic,project,team]`, `sort`, `order` | 스키마 밖의 값은 존재할 수 없다 |
| ② 서버가 존재를 검증·해소할 수 있는 값 | `project: "싱가포르 물류 플랫폼"` → `resolveByName` | 지어내면 0건 → error로 되돌아온다 |
| ③ 최종 자연어 | `reply` | 실행에 쓰이지 않는다 |

**이 셋에 안 들어가는 인자는 스키마에서 없앤다.**

> 판정 질문: **"모델이 이 인자를 틀리게 지어냈을 때 서버가 알아챌 수 있나?"**
> - id → 못 알아챈다(존재하는 남의 id일 수 있다) → **레지스트리로 ②로 강등**(실제 사고 2건 후 도입)
> - 날짜 → 못 알아챈다(형식만 맞으면 통과) → **enum으로 ①로 강등해야 함 (미조치)**

### 판정 기준

- [ ] 프롬프트에 "A는 X할 때, B는 Y할 때 쓴다"가 몇 줄 있는가? **2줄을 넘으면 도구 경계를 다시 본다.**
- [ ] 모든 인자가 위 ①②③ 중 하나인가?
- [ ] 새 도구를 추가하려는데, 기존 도구가 enum 한 칸으로 흡수할 수 없는 게 확실한가?
- [ ] description에 "행동 규칙"(~해야 한다)이 들어가 있지 않은가? (규칙은 프롬프트에 한 번만)

### 현 코드 상태

| 항목 | 상태 | 근거 |
|---|---|---|
| 도구 개수 | **지킴** | 7개 (`search_items`, `get_detail`, `aggregate_items`, `search_users`, `list_pending_reviews`, `get_task_history`, `get_weekly_report`) |
| 부모 필터를 id 아닌 이름으로 | **지킴** | `project`/`epic`/`assignee`/`pm`/`team` 전부 이름 문자열 → `ChatV2ToolSupport.resolveByName` |
| `type`/`sort`/`order`/`group_by`/`role` | **지킴** | enum 지정 |
| **`status` 인자가 enum이 아님** | **위반** | `ChatV2Tools.commonFilters()`의 `status`는 설명 문자열만 있는 자유 string. 값 집합이 계층별로 다르다는 이유로 열어둔 것으로 보이나, 그 결과가 조용한 오답(→ 3축 참조) |
| **날짜 인자가 자유 문자열** | **위반** | `due_date_from/to`, `completed_from/to`가 `YYYY-MM-DD` 자유 입력. 모델이 **주 경계·오늘 날짜를 직접 계산**한다 |
| 도구 경계 (search / aggregate / get_detail) | **압박** | 프롬프트 22~27줄 **6줄**이 판별 규칙에 쓰인다 = 경계가 모델에게 자명하지 않다는 신호 |
| description 비대 | **주의** | `search_items` description이 4줄. 일부가 행동 규칙("~은 get_detail, ~는 aggregate_items")이라 프롬프트와 중복 |

### 조치

- **A-2 (최우선급)** 날짜 인자를 상대 기간 enum으로 접는다.
  ```kotlin
  // 없앤다: completed_from/completed_to, (대부분의) due_date_from/due_date_to
  "period" to str("상대 기간", listOf("this_week", "last_week", "this_month", "next_week")),
  "period_field" to str("기간을 적용할 날짜", listOf("due_date", "completed_at")),
  "overdue" to bool("true면 마감일이 지난 미완료만"),
  ```
  - 서버가 `LocalDate.now(Asia/Seoul)` 기준으로 주 경계를 계산한다 (월~일 규칙을 코드에 한 번만 정의).
  - 절대 날짜(`due_date_from/to`)는 사용자가 "7월 20일부터"처럼 **명시했을 때만** 남긴다.
  - 효과 4겹: 프롬프트 2줄 삭제 / 오답 클래스 하나 소멸 / **eval 케이스가 결정적 단위테스트로 강등**(월말·연말 경계를 LLM 없이 검증) / 스텝당 토큰 감소.
- **A-3** `status`를 enum으로 좁힌다. 계층별 값 차이는 `TODO/IN_PROGRESS/IN_REVIEW/DONE` 합집합 enum + 서버 검증(→ A-6)으로 푼다.
- **A-4** `search_items` / `aggregate_items` / `get_detail` 경계 재검토. 경계를 못 바꾸면 최소한 **결과 데이터로 규칙을 대체**한다:
  `truncated=true`일 때 결과 JSON에 `"counting_hint": "잘린 목록이라 개수·순위 판단 불가 — aggregate_items를 쓰세요"`를 실어 보낸다.
  프롬프트 23줄("반드시 aggregate_items")보다 강하다 — **위반 상황에서만, 모델의 컨텍스트 바로 옆에** 나타나기 때문이다.

## 3. 검증 — 모델 출력은 이중으로 검증한다

### 원칙

모델이 뭘 리턴하든 **1차 스키마 통과 = 검증 완료가 아니다.**

- **1차 (프로바이더/스키마)**: 타입, enum, required, `additionalProperties: false`
- **2차 (애플리케이션)**: 타입·범위·**존재 여부**·권한. 스키마가 통과시킨 값도 앱에서 다시 본다

**검증 실패는 조용히 넘어가면 안 된다.** 조용한 실패(무시·빈 결과)는 환각으로 직결된다:
모델은 "결과 없음"과 "인자가 틀림"을 구분할 수 없어서, 없는 걸 없다고 단정하거나 필터가 안 걸린 전체 목록을 특정인의 업무로 포장한다.

> 실사례: `search_items`에 `assignee_id`를 지어냄 → 조용히 무시됐다면 **무필터 전체 목록**이 "그 사람 업무"로 보고됐을 것.
> → `FAIL_ON_UNKNOWN_PROPERTIES`로 거부하고 error로 되돌리게 고침.

**위험 액션(삭제·결제·발송)은 별도 승인 단계 또는 idempotency key.** 현재 v2 조회 루프에는 위험 액션이 없다(CUD는 보드/폼).
**CUD가 v2로 복귀하는 순간 이 조항이 발효된다** — 그때 사전 승인 없이 tool로 열지 않는다.

### 판정 기준

- [ ] 이 인자가 잘못된 값일 때 응답이 **error인가, 빈 결과인가?** 빈 결과면 위반이다.
- [ ] 모델이 지어낼 수 있는 식별자를 실행 전에 거르는가?
- [ ] 권한 판정이 프롬프트가 아니라 **서버 코드**에 있는가?
- [ ] (CUD 복귀 시) 이 액션은 재실행해도 안전한가? 승인 단계가 있는가?

### 현 코드 상태

| 검증 | 위치 | 상태 |
|---|---|---|
| 스키마에 없는 인자 거부 | `ChatV2ToolSupport.readArgs` + executor의 `UnrecognizedPropertyException` 캐치 | **지킴** — error에 사용 가능 인자 목록까지 실어 보냄 |
| 필수 인자 누락 | `ChatV2ToolArgs`의 non-null 필드 → 역직렬화 실패 → error | **지킴** |
| 지어낸 id 차단 | `ChatV2ToolSupport.validateKnown` + `ChatV2IdRegistry` | **지킴** (사고 2건 후 도입) |
| 이름 → id 해소 | `resolveByName` — 0건/다건/1건을 구분해 error 또는 확정 | **지킴** — 지어낼 id가 없으니 환각 불가 |
| limit 범위 | `SearchItemsHandler`: `(args.limit ?: 10).coerceIn(1, 30)` | **지킴** |
| 권한·스코프 | 핸들러가 부르는 기존 서비스의 `AuthorizationService` | **지킴** — 프롬프트가 아니라 서버가 판정 |
| **잘못된 `status` 값** | `SearchItemsHandler:153-154` 등 — `entries.find{...}`가 null이면 `return emptyList()` | **위반** — **조용한 빈 결과**. 모델은 "그런 상태의 항목이 없다"고 오해하고 사용자에게 단정한다 |
| 위험 액션 승인 | 해당 없음 (조회 전용) | **N/A** — CUD 복귀 시 발효 |

### 조치

- **A-5 (버그)** enum 파싱 실패를 **빈 결과가 아니라 error로** 되돌린다.
  ```kotlin
  // AS-IS: 조용한 오답
  val status = TaskStatus.entries.find { it.name.equals(c.statusRaw, true) }
  if (c.statusRaw != null && status == null) return emptyList()

  // TO-BE: 모델이 자가교정할 수 있는 실패
  if (c.statusRaw != null && status == null) {
      return support.errorResult("task의 status 값이 올바르지 않습니다: '${c.statusRaw}'. 가능한 값: ${TaskStatus.entries.joinToString()}")
  }
  ```
  단, "IN_REVIEW를 epic에 적용" 같은 **계층별 정상 불일치**와 구분해야 한다 — 이건 error가 아니라 "해당 계층엔 그 상태가 없음"으로 결과에 표기.
- **A-6** enum 인자(`status`/`type`/`group_by`/`sort`/`order`/`role`)의 서버측 재검증을 `ChatV2ToolSupport`의 공통 헬퍼로 모은다 (핸들러마다 흩어진 파싱을 한 곳으로).
- **A-7 (문서)** CUD 복귀 시 규칙을 지금 미리 명문화: ①tool로 열기 전 승인 단계 설계 ②idempotency key ③실행 전 사용자 확인 문구. 결정 전까지 CUD tool 추가 금지.

## 4. 히스토리 / 컨텍스트 관리 — 컨텍스트는 자산이 아니라 부채다

### 원칙

1. **역할 경계를 무너뜨리지 않는다.** tool calling 한 턴은 `user → assistant[tool_calls] → tool[result] → assistant[답]`이다.
   이걸 압축·재구성해 저장하면 오염 3종이 발생한다 (A~C안에서 실측됨):
   - **fabrication** — 이전 턴 데이터가 새 답에 샌다
   - **blending** — 이전 요청을 다시 실행한다
   - **mimicry** — 가짜 마커를 앵무새처럼 따라 한다

   → **실제 메시지를 role 태그째 쌓고 그대로 되돌린다** (옵션 D).
2. **trim은 턴 단위로.** 원소 개수로 자르면 `tool_call`만 남고 그 `result`가 잘려 다음 replay 시 API가 거부한다.
3. **컨텍스트에 추가하는 모든 항목은 "이게 없으면 깨지는 eval 케이스"를 동반한다.** 없으면 그냥 토큰 비용이다.
4. **히스토리에는 사람이 실제로 한 말만 `user`로 들어간다.** 시스템이 만든 유도 문구를 `user`로 넣으면 그게 사용자 발화로 replay된다.

### 판정 기준

- [ ] 저장 형태가 **실제 API 메시지 배열 그대로**인가? 요약·마커·텍스트만 저장하면 위반.
- [ ] trim 후에도 모든 `tool_call`에 짝이 되는 `tool` 메시지가 남는가?
- [ ] 히스토리에 들어가는 `user` 메시지가 전부 **사람이 친 문장**인가?
- [ ] 이 컨텍스트 항목이 없으면 깨지는 eval 케이스가 실제로 있는가?

### 현 코드 상태

| 항목 | 상태 | 근거 |
|---|---|---|
| role 태그째 원본 저장 | **지킴** | `ChatV2HistoryStore` 옵션 D (2026-07-20 오염 fix) |
| 턴 단위 trim | **지킴** | `trimToRecentTurns` — `user` 메시지를 턴 경계로 보고 `MAX_TURNS=5` 유지 |
| TTL | **지킴** | 24h, id 레지스트리와 수명 일치 |
| **가짜 `user` 메시지가 히스토리에 저장됨** | **위반(버그)** | `ChatV2Service:101` — `ERROR_RETRY_NUDGE`를 `role="user"`로 주입하고, 종료 시 `messages.drop(turnStart)` 전체를 저장한다. 결과 ①사용자가 그 문구를 말한 것으로 replay ②`trimToRecentTurns`가 이걸 **턴 경계로 세어** 실제 보존 턴 수가 5보다 줄어든다 |
| **id 레지스트리 정책과 프롬프트가 충돌** | **위반(불일치)** | `ChatV2IdRegistry` KDoc: "이전 턴 검색으로 확인된 id는 다음 턴에도 유효" ↔ 프롬프트 15줄: "지난 턴의 id를 기억해 쓰거나 지어내지 말 것 — 이번 턴에 다시 검색". 코드는 허용하는데 프롬프트는 금지 |
| stale 데이터 | **미확인** | 5턴 전 조회 결과가 컨텍스트에 남아 최신값처럼 인용될 수 있다. 측정된 바 없음 |
| eval에서의 오염 | **알려진 리스크** | eval 스펙 §9 — 같은 유저의 케이스가 순차 실행되면 history 누적. 실행 전 `chatv2:history:*` 비우기 필요 |

### 조치

- **A-8 (버그)** `ERROR_RETRY_NUDGE`를 히스토리에서 제외한다. 둘 중 하나:
  - (a) `role="user"` 대신 `role="system"`으로 주입 (턴 경계 오염도 같이 해소), 또는
  - (b) 저장 시 nudge 메시지를 필터링.
  (a)가 원인 제거에 가깝다.
- **A-9 (결정 필요)** id 레지스트리의 멀티턴 정책을 **하나로 확정**한다.
  - **안 1 — 턴 단위 초기화**: 프롬프트대로. 매 턴 재검색을 강제해 stale·오지칭을 원천 차단. 비용: 멀티턴에서 검색 1회 추가
  - **안 2 — 세션 유지 (현 코드)**: "보여줘 → 자세히"가 재검색 없이 이어짐. 대신 프롬프트 15줄을 삭제하고, id의 **실재성만 보장하고 관련성은 모델 몫**임을 명시
  둘 중 뭘 고르든 **프롬프트와 코드가 같은 말을 해야 한다.** 지금은 서로 반대다.
- **A-10** `MAX_TURNS=5`가 필요한 근거를 eval 케이스로 남긴다(4턴 지칭 케이스). 없으면 3으로 줄여 비용을 회수한다.

## 5. 병렬 실행

### 원칙

한 턴에서 모델이 **독립적인** 도구를 여러 개 제안하면(parallel function calling), 순차 실행할 이유가 없다.
같은 턴 안에서 추론되므로 모델 스스로 중복 검색을 피하는 조정 효과도 있다. Gemini 2.5 Flash는 이를 지원한다.

단, **병렬화의 전제는 각 호출이 서로 독립이라는 것**이다. 공유 가변 상태가 있으면 병렬은 버그가 된다.

### 판정 기준

- [ ] 이 도구 호출들이 **서로의 결과에 의존하지 않는가?** (의존하면 모델이 애초에 다음 스텝으로 나눴어야 한다)
- [ ] 병렬 실행 시 건드리는 **공유 가변 상태**가 무엇인가? 그것이 스레드 안전한가?
- [ ] 트랜잭션·영속성 컨텍스트가 스레드를 넘어가지 않는가?

### 현 코드 상태

| 항목 | 상태 | 근거 |
|---|---|---|
| 모델의 병렬 제안 수용 | **지킴** | `toolCalls`가 리스트로 오고 전부 실행 후 각각 `tool` 메시지로 첨부 |
| 실행 | **순차** | `ChatV2Service:121` `toolCalls.forEach { ... }` |
| **병렬화 차단 요인 ①** | | `ChatV2IdRegistry`가 `mutableMapOf`/`mutableSetOf` — **스레드 안전하지 않다.** `resolveByName`이 성공 시 `register`를 호출하므로 병렬 실행 시 race |
| **병렬화 차단 요인 ②** | | 핸들러가 JPA 서비스를 호출한다. 영속성 컨텍스트/트랜잭션은 스레드 바운드 |
| 실측 데이터 | **없음** | 한 턴에 tool_call이 2개 이상 오는 비율이 측정된 적 없다 |

### 조치

- **A-11 (측정 먼저)** eval baseline에서 **"한 턴 tool_call 개수 분포"**를 지표로 추가한다.
  대부분 1개면 병렬화는 이득이 없다 — **측정 없이 병렬화부터 하지 않는다.**
- **A-12 (측정 후 조건부)** 2개 이상이 유의미하면:
  1. `ChatV2IdRegistry`를 동시성 안전하게 (`ConcurrentHashMap` + `synchronizedSet`, 또는 병렬 구간에선 수집만 하고 **합류 후 일괄 register**)
  2. JPA 호출의 스레드 안전성 확인 (각 스레드에서 트랜잭션 새로 열기)
  3. 실패 격리 — 한 호출이 터져도 나머지 결과는 살린다
  4. 로그 순서 보장 (`steps[]`는 **제안 순서대로** 정렬해 재현성 유지)
- **A-13** 병렬 실행을 하더라도 **`steps[]`의 순서와 내용은 결정적으로** 유지한다. eval assert가 여기에 걸려 있다.

## 6. 관찰가능성 & 회귀 테스트

### 원칙

1. **모든 턴의 trace를 남긴다.** 어떤 도구를 어떤 인자로 불렀고 무엇이 돌아왔는지 없으면 디버깅이 불가능하다.
2. **회귀 측정 없는 프롬프트 수정은 무효다.** 프롬프트 한 줄은 국소 수정이 아니라 **전역 수정**이다.
   "이거 고치니 저게 안 돼"의 원인이 정확히 이것이다.
3. **overcall/undercall을 지표로 본다.** 정답에 필요 없는 도구를 부르는 것(overcall)은 비용이자 오답 위험이다.
4. **grounding을 본다.** 최종 답변의 수치가 tool 결과에 실제로 있었는가.

### 변경 절차 (이 축의 핵심 — 반드시 이 순서)

```
1. 실패 발견
2. 재현되는 최소 케이스를 eval에 먼저 추가 → 실패하는 것을 눈으로 확인
3. §1~7 중 어느 축의 문제인지 판정 + 어느 층에서 고칠지 결정
       도구 경계 > 스키마 > 서버 검증 > description > 프롬프트
       (5층 수정은 1~4층이 불가능함을 적은 뒤에만 허용)
4. 수정
5. 전체 재측정 (일부 케이스만 돌리지 않는다)
6. baseline 리포트 갱신
```

### 판정 기준

- [ ] 프롬프트 diff가 있는데 **eval 리포트 diff가 없는가?** 있으면 그 변경은 무효다.
- [ ] 이 실패를 재현하는 eval 케이스가 있는가? 없으면 고치기 전에 먼저 만든다.
- [ ] 사후에 "왜 이 도구를 골랐나"를 추적할 수 있는가?

### 현 코드 상태

| 항목 | 상태 | 근거 |
|---|---|---|
| 응답에 실행 trace | **지킴** | `ChatV2Response.steps[]` = `{tool, arguments, result}` |
| 토큰 로깅 | **지킴** | 스텝별 `in/cached/out`, 완료 시 합계 |
| 요청 로그 | **부분** | `ChatLogService.record` — `logData.recordAction(usage, reply)`. **`steps[]`는 응답에만 있고 영속 저장되지 않는다** |

| grounding 검증 | **없음** | reply의 숫자가 `steps[].result`에 있었는지 아무도 안 본다 |

### 조치

- **A-14 (전체 최우선)** eval baseline 측정을 끝낸다. 스펙 §8 순서 그대로:
  1. `docker exec weekly-report-db psql -U pluxity -c "CREATE DATABASE weekly_report_eval OWNER pluxity;"`
  2. `.\gradlew.bat bootRun --args='--spring.profiles.active=local,eval'` (seed 주입)
  3. `. .\promptfoo\get-cookies.ps1`
  4. `npx promptfoo eval -c promptfoo/promptfooconfig.v2.yaml -j 1` (**`-j 1` 필수** — 동시성이면 유저락 429·레이트리밋)
  **이걸 하기 전에는 A-1~A-13 중 무엇도 "개선됐다"고 말할 수 없다.** 코드 수정보다 먼저다.
- **A-15** `steps[]`를 `chat_logs`에 영속 저장한다. 운영에서 "왜 이렇게 답했나"를 사후 추적하려면 필수.
- **A-16** 지표 3개 추가: **overcall 수**(정답 경로에 불필요한 호출) / **한 턴 tool_call 개수 분포**(→ A-11) / **grounding 위반**(reply의 숫자 토큰이 tool 결과에 없음 → WARN 로그 + eval 메트릭).

## 7. 실패 처리 & 사용자 신뢰

### 원칙

1. **도구 실패는 예외가 아니라 데이터다.** 모델에게 되돌려 자가교정하게 한다 (agent 패턴).
2. **에러는 종류별로 구분해서 준다.** 모델이 대응을 달리할 수 있어야 한다.
   전부 `{"error": "문자열"}`이면 모델은 전부 "죄송합니다"로 처리한다.
3. **error에는 "다음에 할 행동"을 담는다.** 무엇이 잘못됐는지만 알려주면 같은 걸 반복한다.
4. **모르면 모른다고 답하게 한다.** 실패를 그럴싸하게 메우는 것(confabulation)이 가장 나쁜 결과다.
5. **부분 성공을 버리지 않는다.** 3건 중 2건 성공이면 2건으로 답하고 1건만 따로 짚는다.

### 에러 코드 분류 (제안)

| code | 의미 | 모델이 해야 할 행동 |
|---|---|---|
| `NOT_FOUND` | 이름에 맞는 대상 0건 | 이름 변형(음차↔영문, 핵심 단어만) 재시도 → 그래도 없으면 **없다고 사용자에게 알림** |
| `AMBIGUOUS` | 이름 매칭 다건 | 후보를 제시하며 **사용자에게 되묻기** |
| `INVALID_ARGUMENT` | 인자 값/타입 오류, 미지원 인자 | 스키마에 맞게 **인자 고쳐서 재시도** |
| `PERMISSION_DENIED` | 권한 부족 | 재시도 금지. **어떤 역할이 필요한지 사용자에게 안내** |
| `UNKNOWN_ID` | 검색으로 확인되지 않은 id | 먼저 검색 후 결과의 id로 재시도 |
| `TIMEOUT` / `UPSTREAM_ERROR` | 시스템 장애 | 재시도 금지. **일시적 문제임을 사용자에게 알림** |

형태:
```json
{"error": {"code": "AMBIGUOUS", "message": "'물류'에 해당하는 프로젝트가 여러 개입니다: A, B", "next": "사용자에게 어느 것인지 물어보세요"}}
```

### 판정 기준

- [ ] 이 실패를 받은 모델이 **무엇을 해야 하는지 알 수 있는가?**
- [ ] 재시도해도 되는 실패와 재시도하면 안 되는 실패가 **구분되는가?**
- [ ] 실패했는데 모델이 **그럴싸한 답을 지어낼 여지**가 있는가?
- [ ] 부분 성공이 통째로 버려지지 않는가?

### 현 코드 상태

| 항목 | 상태 | 근거 |
|---|---|---|
| 실패를 error 결과로 반환 | **지킴** | `ChatV2ToolExecutor`가 모든 예외를 `{"error": ...}`로 변환. 루프는 계속 돈다 |
| "다음 행동" 포함 | **지킴** | `resolveByName`의 0건/다건 메시지, `validateKnown`, `UnrecognizedPropertyException`(사용 가능 인자 목록 포함) 전부 다음 행동을 담고 있다 |
| 사과로 끝내는 것 방지 | **지킴** | error 직후 모델이 종료하려 하면 `ERROR_RETRY_NUDGE`로 1회 유도 (`MAX_ERROR_RETRIES=1`) — 단 저장 버그 있음(→ A-8) |
| 부분 성공 보존 | **프롬프트 의존** | 프롬프트 19줄에만 있다. 서버는 관여 안 함 |
| **에러 코드 분류** | **위반** | 전부 `{"error": "<한국어 문장>"}` 단일 형태. 권한/없음/모호/인자오류/시스템오류가 구분되지 않는다 |
| **조용한 실패** | **위반** | 잘못된 `status` → 빈 결과 (→ A-5) |
| **도구 실행 타임아웃** | **없음** | LLM 호출엔 `properties.timeoutMs`가 있으나 **도구 실행(DB 조회)에는 타임아웃이 없다** |
| LLM 호출 실패 | **갭** | `send()`의 예외가 루프 밖으로 전파 → 500. 레이트리밋/일시 장애 시 턴 전체가 죽는다 (eval에서 "No output"으로 실측됨) |

### 조치

- **A-18** error 형태를 `{code, message, next}` 구조로 바꾼다 (위 표). `ChatV2ToolSupport.errorResult`를 코드 인자를 받게 고치고 호출부를 이관.
  프롬프트에는 **코드별 대응 원칙 한 줄**만 남기고, 개별 상황 설명은 error 안으로 옮긴다 (프롬프트 예산 회수).
- **A-19** LLM 호출 실패를 루프 안에서 처리한다: 1회 재시도(backoff) → 그래도 실패면 **500이 아니라 안내 reply**로 종료.
  지금까지의 `steps[]`는 살려서 반환한다 (eval의 "No output" 원인 중 하나).
- **A-20** 도구 실행 타임아웃(예: 5s)을 두고 초과 시 `TIMEOUT` 코드로 되돌린다.
- **A-21** grounding 규칙을 프롬프트에 한 줄로 고정: "조회 결과에 없는 값은 말하지 않는다. 모르면 모른다고 한다." (A-16의 측정과 짝)

## 9. 하드 예산 (초과 시 커밋 불가)

수치로 박아두지 않으면 조금씩 늘어난다.

| 항목 | 상한 | 현재 |
|---|---|---|
| 시스템 프롬프트 줄 수 | 40줄 | 37줄 |
| 프롬프트 금지문 (`~말 것`/`반드시`/`절대`) | **5줄** | **9줄 (초과)** |
| 도구 개수 | 7개 | 7개 |
| 루프 최대 스텝 | 8 | 8 |
| 히스토리 보존 턴 | 5 | 5 |

**금지문을 추가하려면 기존 금지문을 지우거나 아래층(도구 경계/스키마/서버 검증)으로 내려야 한다.**
A-2·A-5·A-18을 하면 프롬프트 금지문이 자연히 줄어든다 — 예산 회수가 곧 설계 개선이다.
